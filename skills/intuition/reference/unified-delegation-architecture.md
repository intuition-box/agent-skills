# Unified Delegation Architecture

> **Model (2026-09):** Two-track model with separate wallets for separate jobs.
> Creation attribution carries no semantic weight — position ownership is what
> matters, governed by `deposit`/`redeem`/`withdraw` and the `approve()` model.

## Core Principle

**Creation attribution doesn't carry semantic weight — position ownership does.**

The protocol design is intentional:
- `createAtoms`/`createTriples` have NO `receiver` parameter — attribution follows `msg.sender` by design
- `deposit`/`redeem`/`withdraw` HAVE a `receiver` parameter — shares/value route to `receiver`
- The OWS creates directly; the Hybrid Smart Account deposits/withdraws with `receiver = Main Account`

This is not a gap to work around. It is the protocol working as designed.

## Two Authority Tracks

### Track 1: Creation Authority

**Purpose:** `createAtoms`, `createTriples` (one-time setup operations)

**Wallet:** OWS (Open Wallet Standard) — a temporary wallet with its own keypair

```
OWS creates atoms/triples directly on its own authority.
No delegation chain. No Main Account involvement.
```

**Characteristics:**
- OWS is a temporary wallet generated by the Agent
- The Agent holds the OWS keypair as its primary key
- `msg.sender` at MultiVault = OWS (acceptable — creation attribution is intentional by design)
- No `approve` needed on MultiVault
- No delegation chain needed — OWS acts directly
- After creation is complete, the OWS key can be discarded or retained for future creation

**Setup flow:**
1. Agent generates OWS keypair: `cast wallet new`
2. Fund OWS with tTRUST for creation costs + gas
3. Optional: Upgrade OWS to EIP-7702 for future delegation support
4. OWS creates atoms/triples directly via Path B (standard write operations)

**Agent execution:**
```
OWS (Path B direct call):
  createAtoms(atomData, assets)
Result: msg.sender = OWS, atom created, attribution = OWS (intentional by design)
```

> **Accepted tradeoff:** Removing the Main Account → OWS delegation chain also removes
> the on-chain kill switch and caveat restrictions for the creation track. This is
> intentional — creation attribution carries no semantic weight in the protocol, so
> the chain isn't needed. The only lever is "stop funding OWS," which does nothing
> about balance OWS already holds. If on-chain revocation of creation authority is
> required, a protocol-level change (e.g., a `receiver` parameter on `createAtoms`)
> would be needed.

### Track 2: Deposit/Withdrawal/Redemption Authority

**Purpose:** `deposit`, `redeem`, `withdraw`, batch variants (standing operations)

**Wallet:** Hybrid Smart Account — a deployed contract owned by Main Account

```
Main Account --(owns)--> Hybrid Smart Account (deployed contract)
Hybrid Smart Account --(approve)--> Hybrid Smart Account (on MultiVault)
Hybrid Smart Account --(EIP-712 delegation)--> Agent
```

**Key security property:** The Main Account private key is used ONCE for setup
(deploy Hybrid + approve on MultiVault). After that, the Hybrid signs delegations
via MetaMask popup — the Main Account key is NEVER needed again and is NEVER stored
by the agent or skill.

**Characteristics:**
- Hybrid is a deployed contract (via `SimpleFactory` or signing-page flow)
- Main Account is the owner — no private key exists for the Hybrid itself
- `msg.sender` at MultiVault = Hybrid Smart Account
- `receiver = Main Account` routes shares/value correctly
- Revocable: revoke Hybrid delegation or remove `approve`
- Deposit, withdraw, and redeem all use the same delegation chain — only the inner calldata differs

**Setup flow:**
1. Deploy Hybrid Smart Account:
   - **Signing page (canonical):** `toMetaMaskSmartAccount({signatory: {walletClient}})` triggers MetaMask popup
   - **Manual:** `getFactoryArgs()` → `{factory, factoryData}` → send as plain transaction to `SimpleFactory`
2. Fund Hybrid with tTRUST (direct transfer or ERC-7715 stream from Main Account)
3. Main Account calls `approve(HybridAddress, 3)` on MultiVault (owner-initiated, one-time)
4. Hybrid signs EIP-712 delegation to Agent via MetaMask popup

**Agent execution (deposit):**
```
Agent calls:
  redeemDelegations(
    [Hybrid → Agent],
    deposit(receiver: Main Account, ...)
  )
Result: msg.sender = Hybrid, receiver = Main Account, shares minted to Main Account
```

**Agent execution (withdraw/redeem):**
```
Agent calls:
  redeemDelegations(
    [Hybrid → Agent],
    redeem(receiver: Main Account, ...)
  )
Result: shares burned from Hybrid, TRUST sent to receiver (Main Account)
```

## Withdraw Operations

The withdraw track uses the same delegation mechanism as deposit but targets the `redeem` and `withdraw` operations:

| Operation | Direction | Inner Function | `value` Field |
|-----------|-----------|----------------|---------------|
| `deposit` | TRUST → shares | `deposit(receiver, termId, curveId, minShares)` | deposit amount |
| `redeem` | shares → TRUST | `redeem(receiver, termId, curveId, shares, minAssets)` | 0 |
| `withdraw` | shares → TRUST | Same as `redeem` | 0 |

All use the same `approvalType = 3` (DEPOSIT | REDEMPTION) on MultiVault. The delegation
chain is identical across all three operations — only the inner calldata differs.

**Agent execution (withdraw):**
```
Agent calls:
  redeemDelegations(
    [Hybrid → Agent],
    redeem(receiver: Main Account, shares, minAssets)
  )
Result: shares burned from Hybrid, TRUST sent to receiver (Main Account)
```

## Composition (Full Agent)

For a complete agent that creates, deposits, AND redeems:

```
Phase 1 — Setup (one-time, Main Account key required only for steps 3-4):
  Track 1 (Creation): Agent generates OWS keypair, funds it with tTRUST
                      Optional: Upgrade OWS to EIP-7702
  Track 2 (Deposit):  Deploy Hybrid Smart Account (signing page or manual)
                      Fund Hybrid with tTRUST
                      Main Account approves Hybrid on MultiVault
                      Hybrid signs delegation to Agent (MetaMask popup)

Phase 2 — Operations (Agent autonomous, Main Account key NOT needed):
  Create:   OWS creates atoms/triples directly (Path B)
  Deposit:  Agent calls redeemDelegations([Hybrid→Agent], deposit(receiver: MainAcc, ...))
  Withdraw: Agent calls redeemDelegations([Hybrid→Agent], redeem(receiver: MainAcc, ...))

Phase 3 — Management:
  Creation: OWS key discarded (no on-chain revocation)
  Deposit:  Revoke delegation via disableDelegation (kill switch)
```

## Key Separation (3 roles)

| Role | Owner | Where it lives | May the skill persist it? |
|------|-------|----------------|---------------------------|
| Main Account key | User | MetaMask or hardware wallet ONLY | **NO** |
| Agent key (= OWS key) | Agent | `~/.intuition/agent-wallet.json` (chmod 600) | **YES** |
| Hybrid Smart Account | Main Account (owner) | Deployed contract, NO private key | N/A |

> **The Main Account private key is used once for setup and is NEVER stored by the
> agent or skill.** After deployment and approval, the Hybrid signs delegations
> through MetaMask's standard `eth_signTypedData_v4` popup. The Main Account key
> goes back in the vault/hardware wallet and is never needed again.

## Signing-Page Pattern (Canonical)

The canonical Track 2 setup uses a signing page that triggers a real MetaMask popup:

```ts
import { Implementation, toMetaMaskSmartAccount } from '@metamask/smart-accounts-kit'
import { createWalletClient, custom, createPublicClient, http } from 'viem'

const publicClient = createPublicClient({ chain: intuitionTestnet, transport: http() })
const walletClient = createWalletClient({ chain: intuitionTestnet, transport: custom(window.ethereum) })
const [mainAccount] = await walletClient.requestAddresses()

const hybrid = await toMetaMaskSmartAccount({
  client: publicClient,
  implementation: Implementation.Hybrid,
  deployParams: [mainAccount, [], [], []],
  deploySalt: '0x0',
  signatory: { walletClient },   // triggers real MetaMask popup
})

const signature = await hybrid.signDelegation({ delegation })
```

The resulting `{ ...delegation, signature }` is handed to the Agent off-chain.
Nothing on the Agent's side changes — the delegation is path-agnostic.
